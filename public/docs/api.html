Public API (v1)

REST API for integrations. Create keys under Admin → API (shown once at creation).

Authentication

Authorization: Bearer qh_…your_secret_key…

Optional (less secure): ?api_key=qh_…

API routes are exempt from the site access password; the API key is the only gate.

Never commit keys to git or paste them in public Zaps. Revoke compromised keys in Admin → API.

Base: https://quilthosting.com/api/v1

Bulk member import

POST /api/tenants/:tenantId/members/import powers the CSV importer in Admin → Members → Import.

This is a tenant-admin route authenticated with the admin's JWT session, not an /api/v1 endpoint — API keys cannot call it. It is documented here because it's the primary bulk-write path for members.

Send dry_run: true to run every check and get the full reconciliation without writing anything — no members, no memberships, no custom-field definitions.

Refusals

ConditionResponse
Both rows and raw_rows present400 ambiguous_payload
raw_rows without header400 missing_header
More than 5000 rows400 — split larger files
Two or more columns mapped to the same custom-field key400 duplicate_custom_key, with a duplicates array of { key, headers, indices }

duplicate_custom_key is a real-import-only refusal, raised before anything is written — the second column would otherwise silently overwrite the first. A dry run with the same mapping does not 400; it reports the same problem as a duplicate_custom_key warning instead.

Real import response

{
  "ok": true,
  "batch_id": "…",
  "status": "partial",
  "created": 80, "updated": 35, "skipped": 5,
  "memberships_assigned": 58,
  "membership_failures": 2,
  "level_not_found": 0,
  "plan_limited": 0,
  "custom_fields_created": [{ "key": "guild_number", "label": "Guild #" }],
  "skipped_rows": [{ "row": 12, "reason": "missing or invalid email" }],
  "errors": [{ "row_number": 41, "kind": "membership_failed", "reason": "…", "email": "…" }],
  "warnings": [{ "code": "level_not_found", "message": "…", "count": 3, "sample_rows": [4, 9, 17] }],
  "error_kind_labels": { "membership_failed": "membership(s) failed to assign" }
}

Upsert is keyed on lowercased email; a row whose email already exists on the guild updates that member instead of creating a duplicate.

status

ValueMeaning
runningThe batch row was inserted and has not been closed. Usually an import is executing — but a batch whose started_at is not recent is a leftover from a run that could not close its own record. There are two ways that happens: the Worker isolate was terminated first (CPU/wall-clock limit, eviction), or the closing write itself failed — the failed UPDATE in the catch is best-effort, wrapped in its own try/catch, and only logs if it fails. Nothing sweeps these either way. Only total_rows is written at insert time; every other counter is written solely by the closing update, so a stuck batch still reads 0 no matter how many rows were actually written.
completedNothing was lost.
partialData was not fully imported. Review the batch's errors and warnings.
failedThe run threw. The batch is closed as failed with whatever counts were known and the request returns a 500. Rows already written by an earlier chunk stay written.

completed requires all of: zero skipped rows, zero membership failures, zero plan-limited rows, zero level-not-found rows, and no lossy warning fired. Anything else is partial.

errors vs warnings — not the same thing

errors is per row (which row, what kind, why). warnings is column-level and whole-file: unmapped_column and duplicate_target describe a column, not a row, so they never produce a row-level error.

A batch can legitimately be partial with an empty errors array and a non-empty warnings array — e.g. a CSV with one ignored column that carries data in every row loses a whole column, but no individual row failed. A client that renders only errors shows an unexplained "partial". Render both.
The converse also holds: a completed batch can carry non-empty errors and warnings. Two codes are informational rather than lossy — joined_at_ignored_on_update and level_without_end_date — and neither forces partial. level_without_end_date is the important one: a file that names a membership level but has no renewal/expiry column at all (the commonest Wild Apricot roster shape) makes QuiltHosting choose each renewal date — one full term of the level's duration counted from today. Nothing in the file is lost, but a date was picked on the guild's behalf and the per-row error names exactly which. Render errors and warnings on the completed path too.

Partial caused only by the plan cap

plan_limited > 0 counts toward partial, so a free-plan guild importing 40 people who are not yet active always gets status: "partial" even when their file is perfect. Held rows are not made active: new members come in as pending, existing members are either set to pending or keep the status they already had. The admin UI detects this case (every entry in errors has kind: "plan_limited" and warnings is empty) and phrases it as a completion, not a problem; the "Recent imports" card still shows the partial badge, because the batch-list columns can't distinguish the case reliably.

Re-importing already-active members is free. Only rows that would make someone newly active consume a slot, so a guild sitting at its 30-active limit that re-imports its own unchanged roster comes back with plan_limited: 0 — it is asking the plan for nothing. (plan_limited: 0 is not by itself completed: any other lossy code in the same file still forces partial, and even a completed batch can carry informational level_without_end_date rows.) The trigger is the number of new actives, not the size of the file. The dry run's plan_limit_will_hold estimate applies the same rule, so preview and import agree given the same file, the same mapping, and the same active-member count. That last condition is not under the preview's control: activeSlotsLeft is recomputed from a live count of active members on every request, so a signup, a lapse from the nightly renewal cron, or another admin's import landing in between moves the number. The estimate is a snapshot taken at preview time, not a promise.

Import history

Both routes sit behind the same auth as the import itself and filter by guild.

MethodPathDescription
GET/api/tenants/:tenantId/members/import/batchesThe 50 most recent batches, newest first. Each carries the counters, actor_user_id / actor_email, and a parsed warnings array. No paging parameter.
GET/api/tenants/:tenantId/members/import/batches/:batchId/errorsThe full, uncapped per-row list for one batch, ordered by row number, plus the same warnings array and error_kind_labels. A batch id belonging to another guild returns 404, indistinguishable from one that doesn't exist.

actor_email is a snapshot taken at import time, not a live lookup, so it stays accurate if the account's email later changes or the user is deleted. Both actor fields are null on batches created before the column existed. custom_fields_created is a count on a batch row, but an array of { key, label } in the import response.

What import does not do

  • No rollback. Nothing captures a before-state, so a partial or failed batch cannot be undone. batch_id identifies what happened; it is not an undo handle.
  • Import is not one transaction. Member writes execute as batched statements in chunks of 50, memberships are assigned afterwards per row, and error rows are written after that. A throw part-way leaves earlier chunks written.
  • No resume for a failed batch, and no delta re-import — nothing computes what is still missing.

The supported recovery is to fix the CSV and import it again, which converges because upsert keys on lowercased email. It converges on member records; it does not roll anything back.

Re-import is not monotonic. Membership activation expires the member's existing active memberships before inserting the new one, with no transaction around the pair. If the insert then fails, the expiry is not undone — so re-importing a row that failed to assign a membership to a member who currently has an active membership can leave them with no active membership, strictly worse than before. membership_failed is the one error kind where "just re-run the file" is bad advice: diagnose the failure first. Every other kind is safe to re-import.

Known gap: creating custom fields during an import is a read-modify-write of the guild's settings with no compare-and-swap, so a settings edit committed in that narrow window can be overwritten. The definitions are written before any member row and are not undone if the import later fails. Import never renames, reorders or removes an existing definition.

Full contract, including every warning code and which ones force partial: docs/api.md in the repo.

Zapier / Make

  1. Admin → API → create a key with read scope.
  2. In Zapier: Webhooks by Zapier → GET, or Code by Zapier with fetch.
  3. Schedule a poll on /members or /payments (e.g. every 15 minutes).
  4. Filter for new rows by created_at or store last-seen ids in Zapier Storage.
  5. Map fields into Google Sheets, Mailchimp, QuickBooks Online, etc.

There is no official Zapier app listing yet — custom webhooks cover most guild needs.

Limits & notes

  • Read-focused today; write endpoints may expand later
  • Keys can be revoked; last-used timestamp is recorded
  • Member portal and admin UIs use JWT auth — not the public API key
